# แยกหลังร้านออกจากหน้าร้าน — ดีไซน์

- **วันที่:** 2026-08-06
- **สถานะ:** อนุมัติดีไซน์แล้ว รอเขียนแผนลงมือ
- **ก้อนที่:** 1 จาก 5 (ดูโรดแมปท้ายเอกสาร)

## 1. เป้าหมาย

แยกหน้าจอที่พนักงานหน้าร้านใช้ ออกจากหน้าจอที่เจ้าของใช้ดูแลและตรวจสอบร้าน
ให้เป็นเว็บคนละตัวคนละที่อยู่ โดยที่ POS ทำงานเหมือนเดิมทุกประการ

**จบก้อนนี้แล้วต้องได้:**

- `shop.<domain>` — แท็บเล็ตพนักงาน: ผังโต๊ะ · บิล · จอครัว · คิว QR · เปิด-ปิดกะ · บิลที่ปิดแล้ว
- `office.<domain>` — เจ้าของเปิดจากที่ไหนก็ได้: เมนู · ตัวเลือก · วัตถุดิบ · ผังโต๊ะ&QR · รายงาน 4 หน้า · พนักงาน 3 หน้า · ตั้งค่าสาขา 2 หน้า
- เจ้าของล็อกอินจากบ้านแล้ว **บันทึกจ่ายเงินเดือนได้จริง**
- ทั้งระบบอยู่บน VPS ที่เช่า พร้อม https และ backup ที่ทดสอบกู้คืนแล้ว

**ก้อนนี้ไม่เพิ่มหน้าจอใหม่แม้แต่หน้าเดียว** — เป็นการย้าย ไม่ใช่การสร้าง

## 2. การตัดสินใจที่ล็อกแล้ว

| # | ตัดสินว่า | เพราะ |
|---|---|---|
| D1 | หลังร้านเปิดจากอินเทอร์เน็ตได้ทุกที่ | เจ้าของต้องดูจากบ้าน/มือถือ |
| D2 | API + Postgres ขึ้น VPS ทั้งหมด | เจ้าของเลือกเสียเงินแลกความง่าย โดยรับทราบข้อแลกเปลี่ยนใน §8.1 แล้ว |
| D3 | VPS ในไทยหรือสิงคโปร์ · 2 vCPU · RAM 2–4 GB · Ubuntu | ทุกการแตะปุ่มวิ่งไปเซิร์ฟเวอร์แล้ว โซนไกล = หน่วง 200–300 ms ต่อการกด |
| D4 | หนึ่งโดเมน สอง subdomain | เจ้าของต้องการ "ของขึ้นไปอยู่ด้วยกันหมด แต่แยกของหน้าร้านกับหลังร้าน" |
| D5 | `/api` อยู่ใต้ทั้งสอง subdomain ผ่าน reverse proxy | ได้ same-origin (ไม่ต้องมี CORS) + คุกกี้แยกกันเองอัตโนมัติ + `sameSite: lax` เดิมยังใช้ได้ |

| D7 | หน้าร้านใช้ PIN เหมือนเดิม · หลังร้านใช้อีเมล+รหัสผ่าน | คนละคนใช้ คนละความถี่ คนละกำแพง — ดู §5 |
| D8 | ยังไม่ทำ 2FA แต่สร้างคอลัมน์ `totpSecret` รอไว้ | ตามธรรมเนียมโปรเจกต์: สร้างคอลัมน์รอ ไม่ต้อง migrate ทีหลัง |
| D9 | รวม CI และแก้เทสต์ flaky ไว้ในก้อนนี้ | deploy ต้องมี build pipeline อยู่แล้ว และ CI ที่แดงสุ่มคือ CI ที่คนเลิกอ่าน |

## 3. ขอบเขต

### อยู่ในก้อนนี้

- ย้าย 13 หน้าหลังร้าน + 7 คอมโพเนนต์ + `manage-store.ts` ไป `apps/office`
- สร้าง `packages/web-kit` เก็บโค้ดที่สองเว็บใช้ร่วมกัน
- แยก `api-client.ts` เป็น "ตัวยิง request" กับ "รายการ endpoint"
- ล็อกอินหลังร้านด้วยอีเมล+รหัสผ่าน + ตาราง `Session` + ปิด endpoint ที่เปิดโล่ง
- เขียนเทสต์ขอบเขตบันเดิลใหม่
- Caddy + deploy + backup ที่ทดสอบกู้คืนแล้ว + CI
- แก้เทสต์ flaky 1 ตัว

### ไม่อยู่ในก้อนนี้

- หน้าจอใหม่ทุกชนิด (dashboard วิเคราะห์ · สต๊อก · บัญชี · ลูกค้า) → ก้อน 2–5
- แตก `order.service.ts` (1,974 บรรทัด) — ควรทำ แต่คนละงาน อย่าปนกับการย้าย
- แก้ PIN ฝั่งหน้าร้าน — ทำงานถูกอยู่แล้วสำหรับที่ที่มันอยู่
- แก้ "รับเงินตอนออฟไลน์" — เป็นงานใหญ่ของตัวเอง ดู §8.1
- เทสต์ E2E (Playwright ติดตั้งแล้วแต่ยังไม่มีเทสต์)

## 4. สถาปัตยกรรม

### 4.1 โครงในโปรเจกต์

```
apps/
├── web/          หน้าร้าน — PWA, precache, ทำงานตอนเน็ตหลุด
├── office/       ★ ใหม่ — หลังร้าน, เว็บธรรมดา, ไม่มี service worker
├── api/          ไม่แตะโครงสร้าง เพิ่มเฉพาะ auth (§5)
└── print-agent/  ไม่แตะเลย

packages/
├── shared/       เดิม — เงิน/VAT/สิทธิ์/ใบเสร็จ (ห้ามมี React, ห้ามมี node:*)
└── web-kit/      ★ ใหม่ — โค้ดเบราว์เซอร์ที่สองเว็บใช้ร่วมกัน
```

`packages/web-kit` แยกจาก `packages/shared` เพราะ `shared` มีกฎว่าห้าม import React
หรือ `node:*` (ต้องรันได้ใน service worker) แต่ `session-store` ใช้ zustand + React
และ `route-guards` ใช้ react-router — เข้า `shared` ไม่ได้

**ทำไมเป็นแอปแยก ไม่ใช่ build สองชุดจากแอปเดียว**

ก้อนถัดไปคือ dashboard วิเคราะห์ ซึ่งต้องมีไลบรารีวาดกราฟ (~150–300 KB)
ถ้าสองฝั่งอยู่ในแอปเดียวกัน ไลบรารีนั้นมีโอกาสไหลไปอยู่ใน shared chunk ที่แท็บเล็ตแคช
ซึ่งเป็นบั๊กชนิดเดียวกับที่ `bundle-boundary.test.ts` ถูกสร้างมาดัก
แต่เข้าทางที่เทสต์นั้นไม่ได้มอง

พอแยกเป็นคนละ package **มันเข้าไม่ได้เชิงกายภาพ** — และการ import ผิดฝั่งกลายเป็น
คอมไพล์ไม่ผ่าน แทนที่จะเป็นเทสต์ที่ต้องคอยดูแล

และหลังร้านได้เป็นเว็บธรรมดา ไม่มี service worker ไม่มี IndexedDB ซึ่งถูกต้อง
เพราะหลังร้านต้องต่อเน็ตอยู่แล้ว และ service worker ที่แคชหน้าเงินเดือนค้างไว้
คือแหล่งบั๊ก "ตัวเลขไม่ยอมอัปเดต"

### 4.2 การวางเครื่อง

```
VPS 1 เครื่อง (ไทย/สิงคโปร์, 2 vCPU, RAM 2–4 GB, Ubuntu)
│
├── Caddy ── shop.<domain>   ┬── /       → ไฟล์ static ของ apps/web
│            │               └── /api/*  → Node API (127.0.0.1:3001)
│            └ office.<domain>┬── /       → ไฟล์ static ของ apps/office
│                             └── /api/*  → Node API (ตัวเดียวกัน)
├── Node API (Fastify)
└── PostgreSQL 16
```

**ทำไม `/api` ซ่อนใต้ทั้งสองโดเมน แทนที่จะเป็น `api.<domain>`**

1. **ไม่ต้องมี CORS เลย** — กลายเป็น same-origin ปัจจุบัน API อนุญาต origin เดียว
   (`WEB_ORIGIN`) ถ้าแยกเป็นโดเมนที่สามต้องเปิด CORS ให้สองต้นทางพร้อมส่งคุกกี้ข้ามโดเมน
2. **คุกกี้แยกกันเองอัตโนมัติ** — คุกกี้ที่ `office.<domain>` ตั้ง ไม่ถูกส่งไป
   `shop.<domain>` เซสชันหน้าร้านกับหลังร้านจึงแยกกันจริงโดยไม่ต้องเขียนโค้ด
3. **`sameSite: 'lax'` เดิมยังใช้ได้** ไม่ต้องลดเป็น `none`

Caddy เพราะขอและต่ออายุใบรับรอง https ให้เองอัตโนมัติ — สำคัญสำหรับร้านที่ไม่มีคนดูแลเซิร์ฟเวอร์

**Caddy ต้องส่ง `Host` เดิมต่อไปที่ API** (ไม่ใช่เขียนทับเป็น `127.0.0.1:3001`)
เพราะ §5.5 ใช้ค่านี้ตัดสินว่าคำขอมาจากประตูไหน · ถ้าตั้งผิด endpoint ที่ควรมีเฉพาะ
หน้าร้านจะเรียกได้จากหลังร้านด้วย และจะไม่มีอะไรฟ้อง

**ค่า config ที่ต้องแก้ตามไปด้วย:** จอครัว (WebSocket) และ Raspberry Pi (ดึงงานพิมพ์)
เคยคุยกันในวงแลน ตอนนี้ต้องวิ่งออกเน็ตทั้งคู่

**ตอน dev ยังเป็น cross-origin อยู่** — vite ของหน้าร้าน (`:5173`) กับของหลังร้าน (`:5174`)
คุยกับ API (`:3001`) ข้ามพอร์ต จึงยังต้องมี CORS · `WEB_ORIGIN` ที่ตอนนี้รับค่าเดียว
ต้องเปลี่ยนเป็นรับหลายค่า (คั่นด้วยจุลภาค) และ `env.ts` ต้องตรวจทุกค่าเหมือนที่ตรวจค่าเดียวอยู่ตอนนี้
· production เป็น same-origin จึงตั้งเป็นค่าว่างหรือไม่ตั้งก็ได้

**ยังไม่ได้เลือกชื่อโดเมน** — ทุกที่ในเอกสารนี้ที่เขียน `<domain>` ให้แทนด้วยชื่อจริงตอนลงมือ
ค่านี้ไม่กระทบดีไซน์ ไปอยู่ใน environment variable และไฟล์ Caddyfile เท่านั้น

## 5. การเข้าสู่ระบบ

### 5.1 ปัญหาที่ต้องแก้

`/auth/staff` เรียกได้โดยไม่ต้องล็อกอิน และคืน `{ id, fullName, nickname, role }`
โดยเรียง `role` ขึ้นก่อน (`apps/api/src/modules/auth/auth.service.ts:43`) —
ใครที่เปิด URL ได้จะรู้ทั้ง "ใครคือเจ้าของ" และ "staffId ของเขา" ในคำขอเดียว
ซึ่งเป็นสองอย่างที่ต้องมีก่อนเริ่มเดา PIN · `/auth/branches` เหมือนกัน

PIN 4 หลัก = 10,000 แบบ · ล็อก 5 นาทีหลังผิด 5 ครั้ง = ลองได้ 1,440 ครั้ง/วัน
→ ไล่ครบทุกความเป็นไปได้ใน ~7 วัน ในวงแลนไม่มีใครทำ บนอินเทอร์เน็ตบอททำได้ฟรี 24 ชม.

คอมเมนต์ในโค้ดเขียนสมมติฐานไว้ตรง ๆ ว่า _"a list of shop names on a device that is
already inside the shop's wifi"_ — สมมติฐานนั้นกำลังจะไม่จริง

หลังร้านเก็บเงินเดือน เลขผู้เสียภาษี และ**เลขพาสปอร์ต/ใบอนุญาตทำงานของพนักงานต่างชาติ**
(`Staff.passportNo`, `workPermitNo`) ซึ่งเป็นข้อมูลส่วนบุคคลตาม PDPA

### 5.2 ออกแบบ: สองประตู กุญแจคนละชนิด

| | หน้าร้าน `shop.*` | หลังร้าน `office.*` |
|---|---|---|
| ใครใช้ | แคชเชียร์ · วันละ 5–10 ครั้ง · อยู่ในร้าน | เจ้าของ · วันละ ~1 ครั้ง · ที่ไหนก็ได้ |
| กุญแจ | PIN 4 หลัก (ไม่เปลี่ยนอะไรเลย) | อีเมล + รหัสผ่าน |
| มีรายชื่อให้เลือก | มี | **ไม่มี — พิมพ์อีเมลเอง** |
| อายุเซสชัน | 12 ชม. | 8 ชม. |
| แคชตัวตนลงเครื่อง | มี (ต้องใช้ตอนออฟไลน์) | ไม่มี |

**หน้าร้านไม่เปลี่ยน** เพราะแคชเชียร์เปลี่ยนคนกันตอนคิวยาว ให้พิมพ์รหัสผ่านยาว ๆ
บนแท็บเล็ตกลางร้านจะจบที่กระดาษแปะข้างจอ ซึ่งแย่กว่า PIN + ล็อกบัญชี
PIN ไม่ได้อ่อน มันแค่ต้องอยู่หลังกำแพงที่ถูกที่

**ตรวจแล้วว่าไม่มีหน้าหลังร้านหน้าไหนใช้ "PIN อนุมัติ"** — ทุกกล่อง PIN อนุมัติ
(ยกเลิกรายการ · ส่วนลด · ใบลดหนี้) อยู่ฝั่งหน้าร้านหมด หลังร้านแค่ **ตั้ง** PIN ให้คนอื่น
ซึ่งเป็นงานธุรการ · `apps/office` จึงไม่ต้องขนกลไก Keypad ตามไป

### 5.3 การแฮชรหัสผ่าน

ใช้ **bcrypt (`bcryptjs`) cost 12** ซึ่งเป็นไลบรารีเดียวกับที่ใช้กับ PIN อยู่แล้ว

เหตุผลที่ไม่ใช้ argon2id ทั้งที่แข็งแรงกว่า: `bcryptjs` เป็น pure JS ไม่มี build script
ส่วน argon2 ต้องเพิ่ม native dependency ซึ่งต้องไปแก้ `allowBuilds` ใน
`pnpm-workspace.yaml` และเพิ่มความเสี่ยงตอน deploy บน VPS
สำหรับการล็อกอินวันละครั้ง bcrypt cost 12 (~0.6–1.2 วิ) เพียงพอและยังอยู่ในเกณฑ์ที่ยอมรับได้
บันทึกไว้เป็นทางอัปเกรดถ้าวันหนึ่งมีเหตุให้ต้องแข็งกว่านี้

**นโยบายรหัสผ่าน:** ยาวอย่างน้อย 12 ตัวอักษร ไม่มีกฎบังคับตัวพิมพ์ใหญ่/อักขระพิเศษ
(ตามแนวทาง NIST — กฎพวกนั้นทำให้คนตั้งรหัสที่เดาง่ายในรูปแบบที่คาดเดาได้)

### 5.4 เปลี่ยนที่ฐานข้อมูล

**เพิ่มบน `Staff`** (nullable ทั้งหมด):

| คอลัมน์ | ทำอะไร |
|---|---|
| `email` | ชื่อผู้ใช้สำหรับหลังร้าน · **unique ทั้งระบบ ไม่ใช่แค่ในสาขา** |
| `passwordHash` | bcrypt · **ไม่มีค่านี้ = เข้าหลังร้านไม่ได้เลยแม้จะรู้ URL** |
| `totpSecret` | สร้างรอไว้ ยังไม่ใช้ (D8) |
| `failedLoginAttempts`, `loginLockedUntil` | คู่แฝดของ `failedPinAttempts`/`pinLockedUntil` แต่สำหรับรหัสผ่าน |

`email` ต้อง unique ทั้งตาราง เพราะหน้าล็อกอินหลังร้านไม่มีตัวเลือกสาขา —
อีเมลต้องชี้ไปที่แถวเดียวได้ แล้วสาขามาจากแถวนั้น

**ตารางใหม่ `Session`:**

```prisma
enum SessionSurface { POS  OFFICE }

model Session {
  id        String         @id @default(uuid())
  branchId  String                       // กฎข้อ 1: ทุกตารางมี branchId
  staffId   String
  surface   SessionSurface               // เข้ามาทางประตูไหน
  createdAt DateTime       @default(now())
  expiresAt DateTime
  revokedAt DateTime?
  userAgent String?
  ipHash    String?                      // sha256 ของ IP ไม่เก็บ IP ดิบ

  branch Branch @relation(fields: [branchId], references: [id], onDelete: Cascade)
  staff  Staff  @relation(fields: [staffId],  references: [id], onDelete: Cascade)

  @@index([staffId, revokedAt])
  @@index([expiresAt])
  @@map("sessions")
}
```

JWT พก `jti` ชี้มาที่แถวนี้ · ทุก request ตรวจว่าแถวยังไม่ถูกเพิกถอนและยังไม่หมดอายุ

ได้มาสี่อย่างพร้อมกัน — **logout ที่ฆ่าจริง · ปุ่ม "ออกจากระบบทุกเครื่อง" ·
ไล่พนักงานออกแล้วตัดสิทธิ์ได้ทันทีไม่ต้องรอ 12 ชม. · เจ้าของเห็นว่ามีใครค้างอยู่กี่เครื่อง**

ราคา: query เพิ่ม 1 ครั้งต่อ request (มี index) ซึ่งร้านขนาดนี้ไม่รู้สึก
เรื่องนี้เป็นช่องที่ README ยอมรับไว้เองว่า _"JWT ที่ถูกก๊อปไว้ก่อนหน้ายังใช้ได้จนหมดอายุ"_
พอขึ้นอินเทอร์เน็ตแล้วเลื่อนต่อไม่ได้อีก

**เก็บ session ที่หมดอายุไว้ 90 วันเพื่อการตรวจสอบย้อนหลัง แล้วลบทิ้งด้วย cron**

### 5.5 Endpoint และการปิดช่องที่เปิดโล่ง

**สองประตูคือสอง endpoint คนละตัว ไม่ใช่ตัวเดียวที่เดาเอาเอง:**

| endpoint | ใช้ที่ | รับอะไร | สร้าง session แบบ |
|---|---|---|---|
| `POST /auth/login` (เดิม) | หน้าร้าน | `{ branchId?, staffId, pin }` | `POS` |
| `POST /auth/office/login` ★ | หลังร้าน | `{ email, password }` | `OFFICE` |
| `GET /auth/staff`, `GET /auth/branches` (เดิม) | **หน้าร้านเท่านั้น** | — | — |
| `POST /auth/logout` (เดิม) | ทั้งคู่ | — | เพิกถอนแถว `Session` ด้วย |
| `POST /auth/sessions/revoke-all` ★ | ทั้งคู่ | — | เพิกถอนทุก session ของคนนั้น |

การมี endpoint แยกทำให้ `surface` มาจากเส้นทางที่เรียก ไม่ต้องเดาจาก header
และทำให้กติกาจำกัดการลองผิดของสองฝั่งตั้งค่าแยกกันได้

**ปิดช่องที่เปิดโล่ง:**

- `/auth/staff` และ `/auth/branches` ตอบเฉพาะคำขอที่มาจากโดเมนหน้าร้าน
  (ตรวจจาก `Host` ที่ reverse proxy ส่งมา — ดู §4.2) · หลังร้านไม่มี endpoint เหล่านี้ให้เรียก
- จำกัดการลองผิดสองชั้น: **ต่อบัญชี** (มีอยู่แล้ว ขยายให้ครอบรหัสผ่าน) และ
  **ต่อ IP** โดยใช้ `RateLimiter` ที่เขียนไว้แล้วใน `apps/api/src/modules/qr/rate-limit.ts`
- "ไม่มีอีเมลนี้" กับ "รหัสผ่านผิด" ตอบเหมือนกัน (โค้ดเดิมทำถูกอยู่แล้วสำหรับ PIN)
- เขียน `AuditLog` ทุกครั้งที่ล็อกอินหลังร้านสำเร็จและล้มเหลว

### 5.6 ตั้งรหัสแรก

`pnpm db:seed` รับ `OWNER_EMAIL` และ `OWNER_PASSWORD` เพิ่มจาก `OWNER_PIN` ที่รับอยู่แล้ว
ไม่ใส่ = สุ่มให้แล้วพิมพ์บนจอครั้งเดียว (พฤติกรรมเดียวกับ `OWNER_PIN` ตอนนี้)
เจ้าของตั้ง/แก้อีเมลและรหัสผ่านของคนอื่นได้ที่หน้าพนักงาน

## 6. แผนการย้าย

### 6.1 อะไรไปไหน

| ปลายทาง | ของ | จำนวน |
|---|---|---|
| `apps/office/` | `pages/office/*` (13 หน้า + `routes.tsx`) · `components/office/*` (7 ไฟล์) · เทสต์หลังร้าน · `manage-store.ts` + เทสต์ | 34 ไฟล์ |
| `packages/web-kit/` | ตัวยิง request (~120 บรรทัดที่แกะจาก `api-client.ts`) · `session-store.ts` (125) · `routes.ts` (64) · `business-day.ts` (28) · `route-guards.tsx` (24) | 5 ไฟล์ |

| **ลบทิ้ง** | `office-gate.tsx` + `office-gate.test.tsx` | 2 ไฟล์ |

**ทำไมลบ `OfficeGate` ได้:** มันมีไว้บอกว่า "เปิดหน้าหลังร้านไม่ได้ ต้องต่อเน็ต"
ตอนที่ lazy chunk โหลดไม่ออก พอหลังร้านเป็นคนละเว็บ กรณีนั้นไม่มีอยู่จริงอีกต่อไป
เบราว์เซอร์บอกเองว่าเปิดเว็บไม่ได้ · โค้ดที่แก้ปัญหาที่หายไปแล้ว ต้องหายตาม

**`api-client.ts` (623 บรรทัด) ไม่ยกไปทั้งก้อน** — แยกเป็น "ตัวยิง request" (ไป `web-kit`)
กับ "รายการ endpoint" ที่แต่ละแอปถือของตัวเอง เพื่อให้หลังร้านไม่มีโค้ดเรียก
`/orders/:id/pay` ติดไปด้วย และเพื่อให้ auth สองฝั่งแยกกันได้จริงโดยไม่ชนกัน

**สองอย่างที่จงใจไม่ย้าย ทั้งที่ดูเหมือนงานหลังร้าน:**

- **`/bills`** อยู่หน้าร้านต่อไป เพราะลูกค้าเดินกลับมาขอใบกำกับภาษีตอนร้านเปิด ·
  คอมเมนต์ใน `business-day.ts` เขียนเหตุผลนี้ไว้แล้ว
- **`/manage/tables`** อยู่หลังร้านตามเดิม · วันที่ต้องพิมพ์สติกเกอร์ QR ใหม่ตอนร้านเปิด
  จะต้องเปิดอีกเว็บหนึ่ง ซึ่งยอมรับได้เพราะเป็นงานที่ทำปีละครั้ง

### 6.2 เกณฑ์ตัดสินว่าย้ายสำเร็จ

> **เทสต์ที่ย้ายไปทุกตัวต้องผ่าน โดยแก้ได้แค่บรรทัด `import`**
> ถ้าต้องแก้ `expect` แม้แต่บรรทัดเดียว แปลว่าพฤติกรรมเปลี่ยน = ย้ายผิด

สถานะฐาน วัดไว้เมื่อ 2026-08-06:

| ชุด | ผล |
|---|---|
| `@pos/shared` | 405 ผ่าน |
| `@pos/print-agent` | 15 ผ่าน |
| `@pos/web` ทั้งหมด | 364 ผ่าน |
| — เฉพาะที่จะย้ายไป `apps/office` | **12 ไฟล์ · 112 เทสต์** |
| — ที่เหลืออยู่กับ `apps/web` | 252 เทสต์ |
| `@pos/api` | ต้องมี Postgres จึงจะรันได้ (ยังไม่ได้วัด) |

**ตัวชี้วัดที่เป็นตัวเลขอีกสองตัว:**

- ขนาดที่แท็บเล็ตแคชต้องลดลงจริง — ฐานปัจจุบัน หน้าร้าน 296,843 bytes · หลังร้าน 389,783 bytes
- `apps/office` ต้องไม่มี service worker และไม่มี IndexedDB เลยแม้แต่บรรทัดเดียว

### 6.3 เทสต์ขอบเขตชุดใหม่

`bundle-boundary.test.ts` เดิม 6 เทสต์พิสูจน์ขอบเขตภายในบันเดิลเดียว พอแยกแอปแล้ว
โจทย์เปลี่ยนรูป ของใหม่ต้องพิสูจน์:

1. `dist` ของหน้าร้านไม่มีร่องรอยของหลังร้านเลย (ไม่ใช่แค่ไม่ได้ precache)
2. `sw.js` ของหน้าร้าน precache หน้าที่ต้องเปิดได้ตอนเน็ตหลุดครบทุกหน้า
3. `apps/office` build ออกมาแล้วไม่มี service worker
4. `apps/office` import อะไรจาก `offline/` ไม่ได้เลย

ข้อ 4 เป็นกำไรของ D6 — เดิมเป็นเทสต์ที่ต้องคอยดูแล ตอนนี้กลายเป็นสิ่งที่เขียนผิดแล้ว
คอมไพล์ไม่ผ่าน

### 6.4 ลำดับ

แต่ละขั้นต้องเขียวก่อนไปต่อ

1. สร้าง `packages/web-kit` ยกไฟล์ที่ใช้ร่วมขึ้นไป — **ยังเป็นแอปเดียว เทสต์ 364 ตัวต้องเขียวครบ**
2. แยก `api-client` เป็นตัวยิง + รายการ endpoint
3. สร้าง `apps/office` เปล่า ให้ build ผ่านก่อน
4. ย้ายหน้า + เทสต์หลังร้านเข้าไป
5. ถอด `lazy()` / `OfficeGate` / `globIgnores` ออกจาก `apps/web` + เขียนเทสต์ขอบเขตใหม่
6. auth ฝั่ง API (ตาราง `Session` · รหัสผ่าน · ปิด endpoint ที่เปิดโล่ง)
7. หน้าล็อกอินของหลังร้าน
8. Caddy + deploy + backup + CI

**ขั้น 1 สำคัญกว่าที่เห็น** — เป็นขั้นที่แยกความเสี่ยงออกจากกัน ถ้าแกะไฟล์ออกมาแล้ว
เทสต์เดิมยังเขียวครบโดยที่ยังเป็นแอปเดียว แปลว่าการแกะไม่ได้ทำอะไรพัง
จากนั้นค่อยเจอปัญหาเรื่อง "สองแอป" ทีละเรื่อง

## 7. ปฏิบัติการ

### 7.1 Backup

ข้อมูลอยู่ที่เดียวบน VPS ไม่มีสำเนาในร้านอีกแล้ว

- `pg_dump` อัตโนมัติทุกวัน → เก็บบนเครื่อง 7 วัน + **ส่งออกนอกเครื่อง** (Backblaze B2 / S3) 30 วัน
- **ต้องลองกู้คืนจริงหนึ่งครั้งก่อนเปิดร้าน** — backup ที่ไม่เคยกู้คือ backup ที่ยังไม่รู้ว่ามีจริงไหม
- เป็นงานที่ต้องเสร็จในก้อนนี้ ไม่ใช่ไว้ทำทีหลัง

### 7.2 CI

ตอนนี้ไม่มี `.github/` เลย ทั้งที่มีเทสต์กว่า 1,100 ตัว typecheck และ lint ที่พร้อมใช้

GitHub Actions รัน `typecheck` → `lint` → `test` ทุก push
โดยยก Postgres ขึ้นเป็น service container แล้ว `db:deploy` + `db:seed:demo`
ก่อนรันเทสต์ของ API (เทสต์ API ยิงฐานข้อมูลจริงและต้องการเมนูจาก seed demo)

### 7.3 แก้เทสต์ flaky

`apps/web/src/pages/office/PayrollPage.test.tsx` เทสต์ `"commits a day count on blur,
not on every keystroke"` ล้มแบบสุ่มตอนรันชุดเต็มบนเครื่องที่โหลดหนัก
(รันไฟล์เดี่ยวผ่าน · รันชุดเต็มรอบสองผ่าน 364/364)

สาเหตุคือ race ระหว่าง `useEffect` ที่ reset state จากค่าเซิร์ฟเวอร์
(`PayrollPage.tsx:339`) กับ `fireEvent.change`/`blur` ในเทสต์
แก้โดยครอบ assertion ด้วย `waitFor`

ต้องแก้ก่อนตั้ง CI ไม่งั้น CI จะแดงสุ่ม ๆ แล้วคนจะเริ่มมองข้าม

## 8. ความเสี่ยงที่รับไว้แล้ว

### 8.1 เน็ตร้านล่ม = ร้านรับเงินไม่ได้

ระบบนี้ **รับเงิน · ส่งครัว · พิมพ์บิล ตอนออฟไลน์ไม่ได้โดยการออกแบบ**
เลขที่ใบเสร็จต้องออกจากเซิร์ฟเวอร์ (กฎข้อ 9 · `assertCanIssueOffline`)
พอ API ขึ้น VPS แล้ว "เน็ตล่ม" จึงเท่ากับ "หยุดขาย" ไม่ใช่แค่ "ดูรายงานไม่ได้"

เจ้าของเลือกทางนี้โดยรับทราบข้อแลกเปลี่ยนแล้ว (D2)

**ตัวลดความเสี่ยงที่ต้องมี:** เราเตอร์ 4G สำรอง (หรือแท็บเล็ตแชร์เน็ตจากมือถือ)
ทำให้ต้องล่มพร้อมกันสองทางถึงจะหยุดขาย · เป็นข้อกำหนดปฏิบัติการ ไม่ใช่งานเขียนโค้ด

**ทางแก้ระยะยาว** คือทำ "รับเงินตอนออฟไลน์" ให้ได้ ซึ่งต้องออกแบบเลขเอกสารต่อเครื่องก่อน
เป็นงานใหญ่ของตัวเอง ไม่อยู่ในก้อนนี้

### 8.2 ข้อจำกัดเดิมที่ยกมาด้วย ไม่ได้แก้

- **เจ้าของที่ดูแลสองสาขา** มี `Staff` คนละแถวต่อสาขา จึงต้องมีคนละอีเมล ·
  README ระบุช่องนี้ไว้แล้วในหัวข้อ "บทบาทเจ้าของเฉพาะสาขาตัวเอง" ·
  `/settings/all-branches` ยังดูยอดขายทุกสาขาจากเซสชันเดียวได้เหมือนเดิม
- **สาขาที่สองที่อยู่คนละสถานที่** ใช้ API ตัวเดียวกันผ่านอินเทอร์เน็ต จึงเจอ §8.1 เหมือนกัน
